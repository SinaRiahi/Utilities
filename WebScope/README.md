# WebScope

WebScope is a website **informer** for AI-assisted scraper development. Give it one URL and optional known variables. It loads only that page, observes what the page itself requests, captures useful response bodies, correlates known values, and produces an **agent evidence bundle**.

It does **not** crawl discovered links and it does **not** generate or run a scraper.

## Can an agent use it to build a scraper?

Yes. That is the intended workflow:

1. Give WebScope the target URL.
2. Optionally provide known values such as `price=100`, `product=Example`, or `availability=In Stock`.
3. WebScope observes the rendered page and its network traffic.
4. WebScope exports a ZIP containing the evidence.
5. Give that ZIP to your coding/AI agent.
6. The agent uses the observed API endpoints, request details, response bodies, variable matches, and page evidence to implement the actual scraper.

The informer stops at evidence collection. The agent remains responsible for deciding how the final scraper should work.

## Evidence bundle

Every investigation produces one ZIP with a structure similar to:

```text
webscope-evidence-....zip
├── manifest.json
├── report.json
├── agent_instructions.md
├── scan_summary.json
├── target.json
├── page/
│   ├── rendered.html
│   ├── visible_text.txt
│   ├── scripts.json
│   ├── links.json
│   ├── forms.json
│   ├── json_ld.json
│   └── embedded_json.json
├── variables/
│   ├── index.json
│   ├── price.json
│   ├── product.json
│   └── availability.json
├── network/
│   ├── requests.json
│   ├── responses.json
│   └── api_endpoints.json
└── api_responses/
    ├── index.json
    ├── 0001_get_product/
    │   ├── meta.json
    │   └── body.json
    ├── 0002_get_reviews/
    │   ├── meta.json
    │   └── body.json
    └── ...
```

### Why responses are separated

A modern website can expose very large API responses. Putting all of them into one JSON report makes the bundle difficult for agents to consume and can exceed context limits.

Each observed API response therefore gets its own directory:

- `meta.json` — URL, method, status, content type, headers, request relationship, size, hash, and body filename.
- `body.json` — pretty-printed JSON when the response is JSON.
- `body.bin` — raw bytes for non-JSON responses.

### Why variables are separated

Each known variable gets its own JSON file containing:

- supplied value
- text matches
- source locations
- JSON paths
- matching API response IDs/endpoints

This lets an agent inspect only the variable evidence relevant to the field it is implementing.

## Security behavior

Authentication and cookie-bearing headers are redacted from exported metadata. WebScope records evidence generated by the target page; it does not intentionally replay or crawl discovered endpoints.

## Requirements

- Python 3.10+
- Google Chrome or Microsoft Edge installed
- Internet access for Python dependencies on first run

## Run

```powershell
python run.py
```

`run.py` creates the virtual environment, installs Python dependencies, detects Chrome/Edge, starts WebScope, and opens the UI.

## Startup

Run only:

```powershell
python run.py
```

The launcher creates/uses `.venv`, installs Python dependencies, detects an installed
Chrome/Edge browser, and starts WebScope. It does **not** run `playwright install chromium`.

The UI is served from `templates/index.html`.


## Scan configuration

The UI exposes two scan controls:

- **Observation time**: how long WebScope keeps observing network activity after the page settles (1–30 seconds).
- **Maximum API responses**: maximum number of API-like response bodies included in the evidence bundle (1–500).

The scan runs as a background job and the UI polls its progress, so long evidence collection/packaging does not leave the page looking frozen.

## Evidence organization

The root `report.json` is intentionally compact. Large page/network evidence is stored in dedicated files, and each API response has its own metadata/body files. API responses are also classified as `primary_data`, `secondary_data`, `page_resource`, or `auxiliary` with a confidence score to help AI agents prioritize useful sources without deleting raw evidence.


## Error handling

WebScope treats individual evidence failures as recoverable whenever possible.
For example, if a variable cannot be matched against one source, the remaining
sources are still analyzed.

Every evidence bundle contains `errors.md`. It lists all recoverable errors and
warnings encountered during the scan. A non-empty `errors.md` does not
necessarily mean the scan failed; the rest of the bundle should still be used.

Fatal errors that prevent the target page from being investigated may still
mark the scan as failed.
